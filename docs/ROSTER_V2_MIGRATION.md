# Roster V2 Migration Contract

Status: design contract for post-v1.17.1 implementation  
Current runtime baseline: v1.17.1, Slices 68–74 merged  
Purpose: define the atomic transition from A–E persisted fields to a roster-native state model without weakening existing tab/thread isolation or creating two writable sources of truth.

## 1. Current checkpoint

The current implementation has intentionally reached this boundary:

```
internal business logic
        ↓
AgentRosterStateAdapter
        ↓
legacy v1.17.1 serialization
(tabA..tabE / labelA..labelE / jobA..jobE)
```

Provider Health, viewpoint binding reads, central background accessors, cloud-job application, tab retirement, saved-binding invalidation, and active rebinding now use the roster abstraction. Remaining A–E writes are compatibility-object construction, not ordinary internal state mutation.

Do not continue mechanically replacing compatibility keys in v1.17.1.

## 2. Problems that prevent F+ today

| Area | Current constraint | Required V2 change |
| --- | --- | --- |
| Capability ceiling | `MAX_LOGICAL_AGENTS = 5` | Make ceiling an explicit policy independent of provider-family count and identity format. |
| Logical identity | `A..E` are both identity and display labels | Introduce stable machine IDs: `agent-1`, `agent-2`, ... |
| Persistence | `tabA/jobA/labelA ... tabE/jobE/labelE` | One authoritative roster collection. |
| Adapter | Projects legacy per-side fields | Become the sole V2 roster repository API, with legacy projection only at compatibility boundaries. |
| Dashboard | `ALL_SIDES = ["A","B","C","D","E"]` | Render from roster descriptors instead of a hardcoded side array. |
| Count control | Maximum comes from `ALL_SIDES.length` | Maximum comes from capability policy. |
| Direct Mesh parser | Explicit `[a-e]` token parser | Resolve stable agent IDs, ordinals, aliases, and labels without a fixed regex range. |
| Cloud schema | v1 top-level `jobA/jobB/jobC`, overlay extends D/E | Introduce cloud schema v2 with a bounded roster profile. |
| State schema | `STATE_VERSION = 3` | Introduce a new state version with one-way validated migration from v3. |
| Tests | Intentionally assert max=5 and reject count 6 | Split compatibility tests from V2 capacity tests. |

## 3. Identity model

Machine identity MUST NOT be a letter.

Canonical logical-agent ID:

```
agent-<positive base-10 integer>
```

Examples: `agent-1`, `agent-5`, `agent-27`.

Rules:

- IDs are generated by AI Bridge, not accepted as arbitrary object-property names from provider pages.
- Valid ID regex: `^agent-[1-9][0-9]*$`.
- `__proto__`, `constructor`, `prototype`, arbitrary strings, and negative/zero ordinals are impossible by construction.
- The numeric ordinal is presentation/order metadata, not provider identity.
- First-five legacy aliases may be A–E for compatibility, but aliases are not primary keys.
- Display labels/personas remain user-controlled text and must never be treated as identity.
- Provider family is independent from logical-agent identity.
- Chrome tab ID is runtime binding authority, never public identity.
- Sanitized conversation thread identity remains separate from both logical ID and browser tab ID.

This model deliberately does not cap identity at 26 agents.

## 4. Proposed authoritative state shape

The exact implementation may evolve, but V2 MUST have one authoritative roster representation equivalent to:

```js
{
  stateVersion: 4,
  roster: {
    version: 2,
    nextOrdinal: 6,
    agents: [
      {
        id: "agent-1",
        ordinal: 1,
        legacySide: "A",
        label: "AI A",
        job: "...",
        tabId: 123
      }
    ]
  }
}
```

Security requirements:

- `agents` must be an Array, never an attacker-controlled object map.
- The roster must reject duplicate `id`, duplicate `ordinal`, and duplicate bound `tabId`.
- The configured maximum is enforced before allocation and on load.
- `tabId` remains a positive integer or null.
- `label` and `job` retain bounded normalization.
- Unknown properties are dropped during migration/sanitization.
- Runtime objects must be reconstructed by whitelist, not spread blindly from persisted input.

## 5. No dual writable state

The migration MUST NOT persist both:

- authoritative `roster.agents[]`, and
- independently writable `tabA/jobA/labelA...`.

After state v4 activates, V2 roster data is authoritative.

If compatibility code still needs legacy keys, it may receive a short-lived derived projection such as:

```js
legacyProjection(roster)
```

That projection is read-only/ephemeral and is never merged back into authoritative state.

This is the same anti-split-brain rule that motivated Slices 69–74.

## 6. Atomic local-state migration

Migration from state v3 to v4 should occur in one validated transaction:

1. Read the persisted v3 state.
2. Validate/normalize `agentCount` using the v1 compatibility ceiling.
3. Construct V2 agents in deterministic A→E order:
   - A → `agent-1`
   - B → `agent-2`
   - C → `agent-3`
   - D → `agent-4`
   - E → `agent-5`
4. Copy only allowlisted fields: tab binding, label, job.
5. Validate unique positive tab IDs.
6. Convert execution maps to canonical agent IDs only in the same migration release or through a strictly-defined runtime key translator. Never leave two independently mutable map families.
7. Validate all start/current/main/active references.
8. Build the complete state-v4 object in memory.
9. Persist state v4 once.
10. Only after successful persistence replace the live state reference.

On validation failure, retain the original stored v3 object and fail closed with a recoverable migration error. Never partially persist V2.

## 7. Execution-state key migration

The following maps are dynamic today but are keyed by legacy side strings:

- generation identity
- viewpoint identity
- recovery attempts/progress
- last sent/response/delivery state
- phase/review/primary completion state
- round timing/accounting
- source-delivery state

For V2, canonical map keys should be logical agent IDs.

A temporary runtime translator may expose A–E aliases to untouched compatibility code, but there must be exactly one authoritative map entry per logical agent.

Security invariants from the current implementation remain mandatory:

- generation tokens are per logical agent;
- completion commits reject stale/superseded generations;
- sender authority derives from the currently bound Chrome tab;
- same provider + same sanitized thread is rejected;
- same provider + distinct threads is allowed;
- one Chrome tab cannot represent two logical agents;
- same-family sends remain serialized;
- tab close/replacement revokes binding/generation/viewpoint authority;
- replacement tabs are never auto-trusted.

## 8. Cloud settings V2

Cloud settings are profile data, not live-session state. They MUST NOT contain tab IDs, transcript content, generation tokens, viewpoint identities, OAuth material, or source/Vault data.

Proposed V2 profile shape:

```js
{
  schemaVersion: 2,
  agentCount: 7,
  agents: [
    { id: "agent-1", ordinal: 1, label: "Lead", job: "..." }
  ],
  // existing safe profile fields...
}
```

Migration rules:

- Continue accepting schema v1.
- Convert v1 `jobA..jobE` into V2 profile entries on read.
- V2 writes use the roster array as authoritative profile data.
- For a compatibility window, a V2 payload may include a derived first-five `jobA..jobE` projection if needed for older clients; it must be generated from `agents[]` and never treated as a second source of truth by V2.
- If agentCount exceeds five, older clients cannot represent the full roster. V2 must surface this downgrade risk clearly and must never silently discard F+ profiles during a V2 read.
- Cloud whitelist reconstruction and credential scanning remain mandatory.

## 9. Dashboard/UI migration

Post-v1.17.1 UI must render from roster descriptors rather than hardcoded cards.

Each card gets:

- `data-agent-id="agent-7"`
- `data-agent-ordinal="7"`
- optional `data-legacy-side="E"` only when applicable.

Text content rules:

- Labels/personas/provider names/thread badges use `textContent` or equivalent safe DOM construction.
- No raw tab IDs in rendered UI.
- No user/model text through `innerHTML`.
- Shadow DOM, if used, is layout/component encapsulation only and is not a security boundary.
- Color is tertiary identity only; accessible text/status remains primary.

Navigation should use roster ordering with roving tabindex and Arrow/Home/End behavior rather than numeric keyboard shortcuts tied to a fixed maximum.

## 10. Direct Mesh / targeting migration

Do not extend `[a-e]` to another larger hardcoded range.

Target resolution order should become:

1. canonical ID (`agent-12`);
2. explicit ordinal syntax (`AI 12` / `Agent 12`);
3. legacy side alias for migrated first-five agents;
4. unique normalized persona label.

Self-targets and ambiguous labels remain rejected.

Human-readable prompts may still say “AI A” for migrated legacy agents, but routing authority uses canonical IDs.

## 11. Capacity policy

Identity capacity and active-agent policy are separate.

Do not encode the future maximum in the ID format.

The capability contract should eventually expose concepts equivalent to:

- `maxLogicalAgents` — current supported active roster ceiling;
- `maxPersistedAgents` — if different;
- provider-family count — discovery only, never a logical-agent ceiling.

Raising `maxLogicalAgents` happens only after storage, UI, cloud schema, routing, and tests are roster-native.

## 12. Recommended implementation sequence

### Slice 75 — contract/tests only
- Add stable-ID helpers and tests without changing persisted state or the five-agent ceiling.
- Add `agentIdForOrdinal`, `ordinalForAgentId`, validation, and first-five legacy alias helpers.
- No UI behavior change.

### Slice 76 — V2 serializer/migrator in isolation
- Implement pure functions that convert v3 snapshots to a validated V2 object.
- Test malicious keys, duplicates, invalid counts, invalid tab IDs, malformed arrays, and rollback behavior.
- Do not switch production persistence yet.

### Slice 77 — execution-key translation
- Make runtime side-keyed maps accessible through canonical agent IDs while preserving compatibility aliases.
- Keep production persistence v3 until coverage is complete.

### Slice 78 — atomic state-version cutover
- Switch local persistence to state v4/V2 roster as the sole authority.
- Generate ephemeral legacy projections only where unavoidable.
- Full four-platform regression plus migration fixtures.

### Slice 79 — cloud schema v2
- Add v1 read migration and V2 roster profile writes.
- Explicit downgrade/loss prevention for F+.

### Slice 80 — generated roster UI
- Replace hardcoded A–E card inventory with generated cards.
- Keep accessible navigation and safe text rendering.
- Preserve first-five labels for migrated users.

### Slice 81 — raise ceiling
- Only now increase `maxLogicalAgents`.
- Add F+ same-provider/mixed-provider stress tests.
- Verify queue serialization, provider health, recovery, cancellation, and privacy telemetry with the new limit.

## 13. Tests required before F+ ships

At minimum:

- v3 → v4 migration is deterministic and idempotent;
- failed migration leaves original persisted state untouched;
- no duplicate logical IDs;
- no duplicate browser-tab binding;
- prototype keys cannot enter roster state;
- malformed agent IDs fail closed;
- same-provider distinct-thread agents remain valid above five;
- same-provider duplicate-thread agents remain rejected above five;
- tab replacement/close revokes only the intended agent;
- generation completion cannot cross logical IDs;
- cloud V1 loads correctly into V2;
- V2 cloud profiles never expose tab IDs or provenance;
- dashboard renders N cards from roster data without `innerHTML`;
- keyboard navigation works for dynamic N;
- Linux/Unix/macOS/Windows Node suites and Chromium MV3 integration stay green.

## 14. Explicit non-goals during migration

- Do not tie logical-agent count back to provider-family count.
- Do not auto-bind Chrome replacement tabs.
- Do not expose raw Chrome tab IDs.
- Do not weaken exact trusted-provider HTTPS matching.
- Do not parallelize same-family sends merely because more logical agents exist.
- Do not maintain two independently writable roster representations.
- Do not increase the active-agent ceiling before the V2 storage/UI path is complete.
